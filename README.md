# Gainz.Tracker

A personal weight, calorie/macro, and workout-routine tracker. This is the frontend (React SPA); the backend lives in [server/](server/README.md) and has its own README covering the auth/data architecture.

This README is more of a working plan than a finished description — update it as things land instead of leaving it aspirational.

## Where things actually stand

**Built:**

- Real Google sign-in (`src/components/Login.jsx`) — hands off to the BFF, no fake auth.
- Passkey (WebAuthn) sign-in as a second, passwordless option — `src/lib/webauthn.js` wraps the registration/authentication ceremonies; see [server/README.md](server/README.md) for how the crypto side works. Passkeys are managed (added/removed) from the Dashboard.
- `App.jsx` checks session state on load (`/api/me`) and switches between Login/Dashboard. Exposes a `checkAuth`/`onAuthenticated` callback so an in-page login (passkey) can re-check auth state without a page reload, the way a full-page redirect (Google) naturally would.
- `src/lib/api.js` — a small fetch wrapper for talking to the BFF (always sends cookies, throws on non-2xx).
- `src/lib/useLoad.js` + `src/lib/useSubmit.js` — the two shared primitives every card is built on. `useLoad(loader, key)` is fetch-on-mount plus `reload()`; it keeps the last good data across a failed refetch, drops a slow stale response rather than letting it overwrite newer data, and sets state in promise callbacks (never synchronously in the effect body, which `react-hooks/set-state-in-effect` rightly flags). `useSubmit(action, errorMessage)` is the disable → clear error → run → report → re-enable dance every write shares; it shows only your `errorMessage` (never raw API text like "failed with status 500"), unless the action throws a `ValidationError`, whose message is written for the user and shown verbatim.
- `src/lib/sharedData.js` + `SharedDataProvider.jsx` — `/api/me` and `/api/weights` are read by several cards, so they're fetched once at the top of `Dashboard` and read via `useMe()` / `useWeights()`. Whoever writes to one calls its `reload()`, so logging a weight in one card now updates the Big 4 tiers and TDEE estimate in the others without a page reload — previously each card held its own copy and none of them noticed.
- Mobile-first Tailwind design system (`#053345`/`#808F85`/`#DCE0D9`, wireframe-gradient background) applied consistently across every screen.
- **`MacroStatsCard.jsx`** — today's protein/fat/carbs as lifebars against a personal target (editable inline, with the calorie field auto-suggested from the macros via Atwater factors — 4/4/9 — but always overridable), a `g`/`Cal`/`%` display toggle that only changes what's shown, never the bar's fill math, a "Total calories" bar (only once a calorie target exists), inline food logging with a traceable list of today's entries (each removable), and a TDEE calculator inside the targets form (`src/lib/tdee.js`, Mifflin-St Jeor) that estimates maintenance calories from sex/age/activity-level/height/bodyweight and offers Cut/Maintain/Bulk one-tap fills for the calorie field — with a disclaimer, since it's an estimate, and quietly hidden (not guessed) when any input is missing. Today's foods are grouped under the user's own meal slots (default Breakfast/Lunch/Dinner; `MealSlotsForm.jsx` renames, reorders, adds e.g. Dessert) with a subtotal per meal (`groupByMeal` in `src/lib/macros.js`, `MealList.jsx`); food with no matching slot shows under "Other". Any food can be saved for reuse and later logged as N servings (`SavedFood`, macros per one serving; `scaleFood`) — a saved food is a name plus per-serving macros, not an ingredient list. Packaged foods can be looked up by barcode (`ProductLookup.jsx`): scan with the camera (`BarcodeScanner.jsx` — ZXing, loaded only when the scanner opens, EAN/UPC only) or type the number, and the form fills from Open Food Facts scaled to the grams eaten; values are per 100 g at the source, so `scaleFood` does the scaling. The camera needs https or localhost, so testing on a phone over the LAN needs a tunnel — the typed number is the fallback. Open Food Facts is community-edited, so the form says to check the numbers against the pack.
- **`GettingStarted.jsx`** — a first-run card above the macros card, for new users only. The calorie estimate needs a profile (sex, age, activity), a height and a weight, which live on other pages; rather than reorder the page for everyone, this lists those two prerequisites and disappears once they exist. Visibility is derived from the data (`onboardingSteps` in `src/lib/onboarding.js`, which also defines what "profile complete" means for the profile page and the dashboard badge), so there's no dismissed-flag to store or get out of sync.
- **`Footer.jsx`** — a "Made by" line and a native `<dialog>` crediting the open-source pieces. Open Food Facts is listed with its ODbL licence because that licence requires attribution; when adding a dependency or data source that needs credit, add it to `CREDITS` in this file.
- **`WeightChart.jsx`** — weight and body-fat progression (via the shared `StatLineChart.jsx`), inline weight logging (with optional body fat %), a one-time editable height, a derived BMI (never stored — computed from the latest weight entry + height each render), weight/body-fat goals shown as a yellow chart reference line (deliberately distinct from the muted strength-standard lines on the Big 4 chart), a "both" mode that stacks the two as aligned panels (never one dual-axis chart), and a 1W–1M–3M–6M–1Y–All range picker (defaults to 1Y) that filters client-side against the already-fetched entries. X-axis ticks only grow a year suffix ("Sep '26") when the visible range actually spans more than one calendar year. While there are no weight entries the card shows one first-run form (`MeasurementsForm.jsx`: weight, body fat, height, and the optional goals) instead of the separate height/goals/log controls; it writes the profile first and the weight second, so a retry after a failure can't log the weight twice.
- **`TrainingLogCard.jsx`** (+ `RoutineEditor.jsx`) — a training split (e.g. "6-Day PPL") as a list of day-type labels you pick from in any order (`src/lib/templates.js` holds five named presets, plus a custom builder), not tied to calendar weekdays. Each day you choose which one you did (`DayLogForm.jsx` — the split's order only preselects a suggestion, via `src/lib/splits.js`) and mark it done or skipped, capped at one log per calendar day (enforced server-side, not just in the UI — see `server/README.md`); the streak counts consecutive completed logs. History is a real month calendar (`TrainingCalendar.jsx`), not a flat list — click any past day and the logger above the calendar retargets to it (the day is highlighted; clicking today, the same day again, or outside the card goes back to today), so a missed day is filled in with the same controls; a logged day can have its type changed, be flipped done/skipped, or be removed (removal asks first, since it also deletes that day's exercises and can't be undone). Routine setup (rare) and daily logging (frequent) share one card; the editor only mounts while you create or change a routine, and a single dependent load feeds both. A "Done" day (never a skipped one) can carry a session log — arbitrary exercises + weight/reps and a manual duration in minutes, via the shared `SessionEditor.jsx`, opened either right after marking a day done or later from the calendar's day-detail panel. Editing a session deletes and recreates its `WorkoutSet` rows rather than diffing them — simpler, and these rows are only ever queried by the session they belong to, never by their own timestamp, so that's free.
- **`BigFourCard.jsx`** — logs squat/deadlift/bench/overhead press via the existing (previously unused) `/api/workout-sets`, ranks the four by each lift's most recent weight, and charts progression per lift (also via `StatLineChart.jsx`) against an optional goal (yellow line) plus four toggleable Novice/Intermediate/Advanced/Elite strength-standard lines (muted, `src/lib/strength.js`) converted to this person's kg from their bodyweight and sex. A tap-to-reveal (?) explains the ranking/rating logic — a native `title` tooltip won't fire on touch, so this is a click-toggled panel instead. The full log list is collapsed behind a "Recent logs (N)" toggle rather than capped, since collapsing (not truncating) is what keeps a growing history from cluttering the card.
- **`ProfileSecurityPage.jsx`** — full profile (avatar/name/email), `sex`/`age`/`activityLevel` (feeds the Big 4 strength rating and the TDEE calculator — optional, nothing else reads them), and passkey management, all pulled off the dashboard onto a separate screen reached via a compact top bar. Deliberately not one tap away on the page you land on every visit, since adding a sign-in credential is security-sensitive.
- `Dashboard.jsx` composes the cards above into a `grid grid-cols-1 lg:grid-cols-2` — single column on mobile, 2-up on desktop — plus the compact profile bar and a `view` state (`dashboard`/`profile`) that swaps the page content in place of real routing (see Open questions below).

**Not built yet:** `WorkoutRoutine`'s `exercises`/target-sets/reps fields — session logging (above) is actual-performance logging, not a planned routine, and nothing links a split day-label to a specific `WorkoutRoutine` yet. That's still the natural extension point described below.

## Why React + Vite + Tailwind

Kept deliberately boring: Vite for fast dev/build with no framework opinions forced on us (no server rendering, no file-based routing we don't need for what's currently a single authenticated app, not a public site), React because it's the most transferable choice for a learning project, Tailwind for styling so we're not hand-rolling CSS files per component as the app grows.

Every component uses Tailwind utility classes exclusively — no per-component CSS files. The one exception is `src/index.css`, which holds the Tailwind import plus `.app-background` (the shared wireframe-grid/gradient background), since a `mask-image` with multi-stop gradients isn't expressible as Tailwind utilities. **Whatever component is built next should stay Tailwind-only**, so this doesn't drift back into mixed approaches.

## How the frontend talks to the backend

The SPA never touches Google, tokens, or the database directly — it only calls the BFF (see `server/`) via relative paths (`/api/...`, `/auth/...`), which the Vite dev server proxies to `localhost:4000` (config in `vite.config.js`). This means:

- No `.env` is needed on the frontend in dev — there's nothing to configure, the proxy makes everything same-origin.
- Every call needs `credentials: 'include'` so the session cookie actually gets sent — `src/lib/api.js` does this automatically, so new code should go through that helper rather than calling `fetch` directly.
- Google login is a full-page navigation (`window.location.href = '/auth/google'`), not a `fetch` call — that's an OAuth requirement, not a frontend choice, and should stay that way if this ever gets a second SSO provider. Passkey login/registration, by contrast, are `fetch`-based (`src/lib/webauthn.js`) since WebAuthn ceremonies run via the browser's `navigator.credentials` API, not a redirect.

## Planned feature build-out

1. **Planned routines** — the remaining gap. Session logging (see `SessionEditor.jsx` above) covers *actual* performance per training day; it deliberately does not cover *planned* performance — `WorkoutRoutine`'s structured exercise list (target sets/reps) still has no frontend, and nothing links a split's day-label to a specific `WorkoutRoutine`. That linkage, plus a planned-vs-actual comparison view, is the natural next layer, sitting on top of both `WorkoutSplit` and the now-used `WorkoutSet`/`SplitLog` — not a replacement for either.

## Open questions to decide before/while building the above

These are real open decisions, not settled defaults — flagging them here so they get made deliberately instead of by accident:

- **Routing.** `Dashboard.jsx` now has two "pages" (dashboard/profile) via a plain `view` state, not `react-router-dom` — a URL toggle would need one more screen or an actual need for a bookmarkable/shareable URL or back-button support before it's worth the dependency.
- **Client state / data fetching.** Resolved for now with `useLoad`/`useSubmit` and the shared `/api/me` + `/api/weights` resources above — about 60 lines of hook plus a context, rather than a data-fetching library. Genuine needs for request deduping across many components, caching, or optimistic updates are the point to reach for TanStack Query — not before.
- **Units.** The backend schema is metric-only (`weightKg`, `heightCm`). If imperial units matter, that's a backend + frontend decision to make together — now that real weight/height data exists, retrofitting a unit system means a migration choice (convert stored data vs. store a unit preference), not just a frontend formatting change.

## Running locally

This only runs meaningfully against the BFF — see [server/README.md](server/README.md) for the full backend setup (Postgres + Google OAuth credentials). Once that's running on `:4000`:

```bash
npm install
npm run dev      # starts on :5173, proxies /api and /auth to :4000
```

`npm run lint`, `npm test` (Vitest, `npm run test:watch` for watch mode), and `npm run build` all work standalone without the backend running (they don't need a live connection), and are worth running before committing. Tests cover the pure logic in `src/lib/` (strength tiers, TDEE, streaks, dates, macro/BMI math, the `api` wrapper, `useSubmit`'s ordering contract) — deliberately not components; there's no jsdom/testing-library here, so logic that's worth testing belongs in `src/lib/`, not trapped in a component. Note that in dev, React StrictMode double-invokes every mount effect, so request counts in the network tab are doubled versus a production build — `eslint.config.js` explicitly excludes `server/` since that's a Node app, not a browser one, and gets its own conventions.


## Deploying (Render + Neon, free)

One Render web service runs the BFF *and* serves the built client (`server/src/app.js` does that only when `NODE_ENV=production`), so the browser sees a single origin — no CORS, first-party cookies, and the passkey origin is just the site. Postgres is on Neon; Render's own free database is deleted after 30 days. [`render.yaml`](render.yaml) describes the service.

1. **Neon**: create a project and copy the connection string that is *not* the pooled one (the host has no `-pooler`). It's the right choice for a single small server, and it's what `prisma migrate` needs. Append `&connect_timeout=15` — Neon suspends an idle database and the first query after a nap takes a moment.
2. **Render**: New → Blueprint → pick this repo. It asks for the `sync: false` variables in `render.yaml`. `SESSION_SECRET` is generated for you. Set `DATABASE_URL` to the Neon string and `FRONTEND_URL` to `https://<service-name>.onrender.com` (no trailing slash; you know the name before the first deploy finishes, since you choose it).
3. **Google Cloud Console** → your OAuth client: add `https://<service-name>.onrender.com/auth/google/callback` as an authorized redirect URI, and set the same value as `GOOGLE_REDIRECT_URI` on Render. Leaving this out is the usual reason the first login fails.
4. Deploy. The build runs `prisma migrate deploy` against Neon, so the schema is created (or updated) on every deploy and a failing migration stops the deploy rather than the running app.

Things that behave differently from local:

- **Cold starts.** A free Render service sleeps after 15 minutes without traffic and takes about a minute to wake. `GET /healthz` is a database-free endpoint if you ever want an external pinger to keep it awake (750 free hours a month covers one service running all month).
- **A new database is empty.** Signing in creates a fresh user. Local data stays local unless it's dumped and restored.
- **Passkeys don't carry over** — they're bound to the domain they were registered on.
- **The camera scanner needs https**, which Render provides, so barcode scanning works from a phone there.
- Changing `SESSION_SECRET` signs everyone out. Changing the site's domain later means updating `FRONTEND_URL`, `GOOGLE_REDIRECT_URI` and the Google console entry together.
